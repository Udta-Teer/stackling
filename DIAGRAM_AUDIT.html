STACKLING · FULL DIAGRAM AUDIT · 19 JULY 2026

Strong inventory. Weak diagram language.

Implemented after audit

All findings below are now closed in source: 497 states fit the 360px mobile frame with no clipped labels or overlap; all 1,224 flows have explicit edge semantics; failures and denied flows are labeled; CAP and HTTP/2 outliers are repaired; all 132 generated prompts were rewritten; and one exercise in each of 44 units requires the learner to connect the system. These claims are enforced by the browser suite.

Stackling has enough diagrams. The next problem is quality: the renderer clips content on phones, arrows cannot explain what flows across them, and many generated drills reconstruct a topology that has already been revealed instead of making the learner reason about one.

Verdict: do not add more diagrams yet. Repair the renderer and diagram semantics first. The current system is structurally stable but not presentation-safe at the target 360px width.

What is already good

Coverage is no longer the problem

Every unit has 5–15 diagram-bearing exercises. All 44 units contain at least three diagram-retrieval drills.

Structural integrity is mostly clean

Across 497 rendered states: zero missing node references, zero page-level horizontal overflow, zero node overlap, zero edge-count mismatches, and zero browser errors.

Most builds require real placement

186 of 205 build tasks have multiple holes; 83 require at least three components. Only 19 are one-slot completion exercises.

Arrow geometry is repaired

Forward, reverse, and same-column routes terminate at the correct node port. Markers remain aligned with curved paths.

Blocking findings

P0 · LIVE MOBILE DEFECT

282 of 416 diagrams require a tiny horizontal swipe

At 360px, 194 diagrams overflow their frame by 30px and another 88 by 28px. The page itself does not overflow, so automated page-width checks stayed green, but the diagram frame silently clips its right side until the learner swipes. This affects 68% of diagrams.

Cause: the geometry targets roughly 330–332px, while the actual diagram viewport inside page and stage padding is about 302–304px.

P0 · CONTENT HIDDEN

73 diagrams clip node labels

Nodes have fixed heights of 56–60px and overflow:hidden. Long labels and sublabels exceed that height by 1–7px; at least one composite-index label also exceeds width by 15px. The worst visible example is csh-2-5, where the answer-slot instructions are cut off.

Required gate: every node must satisfy scrollWidth ≤ clientWidth and scrollHeight ≤ clientHeight at 360px in both before and after states.

P0 · MISLEADING TOPOLOGY

A network partition is drawn as a server-shaped component

cap-change-1 renders “Replica A → Partition → Replica B” as three boxes with no edges. A partition is a failed or unavailable communication link, not a middle service. The current renderer has no first-class broken-edge state, forcing content authors to turn a relationship failure into a fake component.

P0 · INVISIBLE MULTIPLICITY

Four HTTP connections collapse into one visible arrow

csh-change-1 contains four identical Browser→Origin edges. SVG paints them exactly on top of one another, so the learner sees one arrow while the status says four connections. Multiplicity needs an edge label such as “4 TCP/TLS connections” or visibly separated lanes.

Systemic weaknesses

Zero of 1,215 edges are labeled

The schema supports only from, to, and optional dash. A learner cannot tell whether an arrow means an HTTP request, returned bytes, database read, replication stream, invalidation, queue publication, control-plane lookup, or denied access. Arrow direction alone is insufficient diagram language for system design.

Absence is used as meaning without a visual convention

Broken routes, denied permissions, non-participating followers, and failed links often appear as orphan nodes. Some are intentional before-states, but the visual does not distinguish “intentionally disconnected,” “failed,” “not authorized,” and “author forgot an edge.” Examples include CAP, consensus majority, least privilege, and failed gateway routing.

132 expansion drills are mechanically worded

79 begin “Reconstruct this architecture from memory,” 28 begin “Rebuild the core topology,” 18 begin “Rebuild the complete topology,” and 4 begin “Rebuild the failing topology.” The repeated language exposes batch generation and makes unlike systems feel like the same task.

Most build tasks test reconstruction, not architecture composition

Slots, existing arrows, column positions, and a small palette disclose much of the topology. This is useful retrieval practice, but it should not be counted as proof that the learner can decide components, connections, direction, or boundaries independently.

Repair order

1. Make every diagram fit and every label visible

  1. Derive diagram width from the actual container, not a 430px comment.
  2. Use a ≤300px geometry tier at 360px.
  3. Allow node height to grow from content and recalculate column layout.
  4. Browser-test all 497 states for clipping, overlap, and frame scrolling.

2. Add a real edge vocabulary

  1. Add edge label and kind: request, response/data, read, write, replication, event, invalidation, control.
  2. Add first-class broken, blocked, and optional states.
  3. Render labels without colliding with curves or nodes.
  4. Use multiplicity labels instead of duplicate identical paths.

3. Repair semantically false or ambiguous diagrams

Start with cap-change-1, csh-change-1, intentional orphan states, and all 73 clipped diagrams. Review both viz and afterViz.

4. Rewrite retrieval drills after the renderer is stable

Keep reconstruction where it serves delayed recall, but diversify prompts and add interactions that require connecting edges, selecting boundaries, labeling flows, and diagnosing a changed topology. Do not add more drill count.

Method

Static audit covered every viz and afterViz object in all 44 JSON units. A real Chromium sweep rendered all 416 diagram-bearing exercises at 360×900 and measured page/frame overflow, node intersections, node scroll dimensions, SVG edge count, and JavaScript errors. Four high-risk examples were then inspected visually. Scores are product judgments; counts are computed from the current source.
